# Iteration 012 — фикс OOM MySQL + восстановление SPA

Date: 2026-11-19
Commit: 5f592c9

## Goal
API отдавал 500, SPA не рендерился. Найти и устранить причину.

## Root cause
1. MySQL убивался OOM-киллером (exit 137, 21 рестарт): сервер 1.7 ГБ памяти,
   рядом mailcow, а MySQL 9.4 шёл с дефолтными прожорливыми настройками.
2. После OOM остался **осиротевший процесс mysqld** от уже удалённого контейнера —
   он держал блокировку на ./ibdata1, из-за чего новый MySQL не мог стартовать
   ("Unable to lock ./ibdata1 error: 11").
3. SPA-файлы к этому моменту отсутствовали на диске, и коммит 'git add -A'
   зафиксировал их удаление — восстановлены из 05286d2.

## Changes
- `docker-compose.yml`: MySQL настроен экономно (innodb buffer 64M, fsync,
  performance_schema OFF, max_connections 30) + `mem_limit: 384m`.
- Убит осиротевший mysqld (не mailcow, не текущий moder).
- `www/public/m/` восстановлен из истории git.
- Попутно в `ui.php`: счётчики overdue/future вычисляются до использования;
  `/item/<bad>` -> 404/400 вместо 500; инициализация `$m`.

## Tests
- health: ok (mysql 9.4.0), MySQL 36 МБ / 384 МБ, 0 рестартов, данные целы (33 sent).
- API через домен: /api/queue 200.
- SPA: /m/ 200, рендерит задачу (badge b-sent, rail 1).
- Старый UI: login 302, список 200.

## Notes / next
- Если память снова станет узкой — уменьшить innodb_buffer_pool_size дальше
  или вынести mailcow/moder на разные хосты.
- На будущее: проверять `docker ps -a` и `pgrep mysqld` при 'Unable to lock ibdata1'.
